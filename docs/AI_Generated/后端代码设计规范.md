# OneLauncher 后端代码设计规范

分析日期：2026-10-22。适用范围：以 `OneLauncher.Core` 为主的 C# 后端，以及前端、命令行入口调用后端时的接口边界。

本文依据当前工作区源码整理，是存放于 `docs/AI_Generated` 的分析与设计规范建议，不替代 `docs/AI_Instruction` 中的项目要求。文中的“现状”描述已核实的实现；“约定”面向新增代码及局部维护，不表示旧代码已经全部符合，也不要求为统一码风批量重写历史代码。

## 1. 总体风格与设计取向

当前后端采用直接、务实的面向对象设计：用管理器维护共享数据，用服务组织业务流程，用 Provider 和 Strategy 隔离外部来源及加载器差异。代码以文件作用域命名空间、普通 C# 类型、`Task`、中文注释和显式流程为主，已经使用 `required`、`init`、模式匹配、集合表达式及 JSON 源生成等语言和运行时能力。

应延续的是明确的职责和已有扩展点，而不是每一处历史写法。仓库同时存在旧静态入口、拆分后的服务和未实现的占位类，需要结合实际调用链选择参考。

| 已观察到的风格 | 源码依据 | 新代码的取向 |
| --- | --- | --- |
| 集中创建核心对象，通过 `UnitedCore` 暴露能力 | [UnitedCore.cs](../../OneLauncher.Core/Global/UnitedCore.cs)、[Init.cs](../../OneLauncher.Core/Global/Init.cs) | 复用已有对象和生命周期，不另建一套全局容器 |
| 小型服务负责流程，具体组件负责执行 | [VersionInstallerService.cs](../../OneLauncher.Core/Services/VersionInstallerService.cs)、[GameLaunchService.cs](../../OneLauncher.Core/Services/GameLaunchService.cs) | 服务编排、管理器维护数据、组件执行操作 |
| 同类变化通过窄接口及显式选择表达 | `IJavaProvider`、`IDownloadSourceUrlProvider`、`IModArgStrategy` | 优先接入已有接口，不在多个调用方重复判断同一来源或加载器 |
| JSON 数据根类型、源生成上下文和管理器通常相邻 | [AccountManger.cs](../../OneLauncher.Core/Global/ModelDataMangers/AccountManger.cs)、[VersionListManager.cs](../../OneLauncher.Core/Global/ModelDataMangers/VersionListManager.cs) | 按数据归属组织持久化逻辑，保持序列化契约可见 |
| 进度与状态通过 `IProgress<T>` 和事件向外传递 | [TaskManager.cs](../../OneLauncher.Core/Global/TaskManager.cs)、[LaunchService.cs](../../OneLauncher.Core/DefaultComponent/Launcher/LaunchService.cs) | 后端报告业务事实，前端决定如何显示 |

| 中文 XML 注释、阶段注释和简短表达式成员并存 | `BasicDataManager<T>`、`LaunchCommandBuilder` | 解释契约、顺序和原因，保留容易顺着读的控制流 |

不要求为每个类增加接口，也不要求引入通用仓储、消息总线或新的服务框架。抽象应解决当前确实存在的实现差异、复用或隔离需求。

## 2. 代码归属与前后端边界

### 2.1 当前目录的职责

| 位置 | 当前职责 | 新代码应放入的内容 |
| --- | --- | --- |
| `OneLauncher.Core/Global` | 初始化、核心对象集合、任务、Java 管理和业务异常 | 全局生命周期及跨业务的核心能力 |
| `OneLauncher.Core/Global/ModelDataMangers` | JSON 配置、账户、实例和版本索引的管理与迁移 | 数据根模型、对应管理器及迁移逻辑 |
| `OneLauncher.Core/Services` | 对调用方暴露的安装、资源安装、启动会话入口 | 面向业务用例的编排方法 |
| `OneLauncher.Core/DefaultComponent` | 下载、启动、账户、Java、模组、服务器及联机的具体实现 | 默认组件及其 Provider、Strategy、解析器 |
| `OneLauncher.Core/Minecraft` | Minecraft 版本元数据、资源索引、版本列表和新闻读取 | Minecraft 协议与元数据处理 |
| `OneLauncher.Core/Helper/Models` | `GameData`、`UserVersion`、`UserModel` 等共享模型 | 被多个后端模块使用的数据类型 |
| `OneLauncher.Core/Helper` | 通用辅助功能，以及现有 PCL2 导入实现 | 适合复用的工具；不要将新业务流程一律塞入 `Tools` |
| `OneLauncher` | Avalonia View、ViewModel、UI 消息和异常展示 | 交互、绑定、导航及 UI 线程切换 |
| `OneLauncher.Desktop` / `OneLauncher.Console` | 桌面启动入口 / 命令行调用入口 | 宿主层启动与参数适配 |

`OneLauncher.Core.Net` 仍有旧共享项目及源码，但当前主解决方案未列入该共享项目，`OneLauncher.Core.csproj` 也未导入其 `.projitems`；相应组件已存在于 `DefaultComponent`。新增或维护网络功能时以实际编译的实现为准，不同时维护两份同名逻辑。旧架构说明中将网络实现归入 `Core.Net` 的描述不能直接用作当前代码定位依据。

`InstanceMangerService`、`UserModelService` 当前是空占位类，不作为已落地的分层范例。本文也不规定 JVM Agent 的 Java 代码格式。

### 2.2 后端对前端提供什么

后端接口提供业务模型、查询结果、可等待的任务、取消入口、进度、状态事件和业务异常。后端不引用 Avalonia 控件、ViewModel、`Dispatcher.UIThread` 或 `WeakReferenceMessenger`；当前 Core 源码也没有这些 UI 依赖。

前端负责把进度映射为文案或进度条、将事件切回 UI 线程、通过 `OlanExceptionWorker` 展示异常，以及管理页面和订阅生命周期。后端可以接收认证 SDK 所需的原生窗口句柄，例如 WAM 登录接口，但不持有具体窗口对象。

需要前端感知的变化，应提供事件或明确的结果契约。已有 `TaskManager.OnTaskCreate` 和 `BasicDataManager<T>.OnDataChanged`，调用方应使用它们，避免定时扫描共享状态。若前端任务因后端缺少接口而无法解耦，按[项目必读说明](../AI_Instruction/AGENT_MUST_READ_FIRST.md)的要求，由贡献者补齐后端后再继续前端工作。

## 3. 命名、排版与注释

### 3.1 新增代码的默认约定

| 项目 | 约定 | 示例 |
| --- | --- | --- |
| 命名空间 | 与所属目录一致，优先文件作用域声明 | `namespace OneLauncher.Core.Services;` |
| 类、接口、属性、方法 | PascalCase；接口以 `I` 开头 | `VersionListManager`、`IJavaProvider` |
| 参数与局部变量 | camelCase，表达业务含义 | `versionId`、`gameRootPath` |
| 私有实例字段 | 优先 `_camelCase`；稳定依赖加 `readonly` | `_versionListManager` |
| 布尔值 | 表达可直接判断的含义 | `IsInstalled`、`includeDependencies` |
| 异步方法 | 新增返回 `Task` / `Task<T>` 的方法优先使用 `Async` 后缀 | `RegisterInstalledVersionAsync` |
| 文件名 | 新类型原则上与主类型同名 | `GameLaunchService.cs` |

历史代码中的 `ModelDataMangers`、`Strategys`、`VersionInfomations`、`modType`、`VersionID`、`Play`、`Save`、`InstallNewVersion` 等名称是兼容接口或现有路径。引用时使用真实名称；不要为了符合新约定直接改动已有调用、JSON 字段或反射访问。新增名称使用正确拼写，已有成员只在明确的迁移任务中调整。

### 3.2 排版与表达方式

- 新增 C# 文件使用 4 空格缩进，类型和方法的大括号另起一行；修改旧文件时优先保持局部一致，避免整文件格式化。
- 多参数方法和复杂调用逐行排列；取消令牌通常放在参数末尾。参数多到难以判断含义时使用配置模型，类似 `DownloadInfo`，不要不断叠加互相影响的布尔开关。
- 类型明显时可用 `var`、目标类型 `new()` 和集合表达式；返回类型或业务含义不明显时显式写出类型，不为追求简短牺牲可读性。
- 简单属性和转发方法可以使用表达式体；有校验、资源管理、状态变化的流程使用普通方法体。
- 多步骤分支使用大括号。历史单行 guard 可以保留，不进行与任务无关的统一。
- `using` 放在命名空间之前，清理本次新增的无用引用。当前没有仓库级 `.editorconfig`，不要将某一种排序说成已经被工具强制执行。
- `partial` 文件按规划、执行、参数构建等职责拆分；`#region` 只用于清楚的逻辑分组，不用它掩盖需要拆分的长方法。

### 3.3 注释

以中文说明业务原因、边界和生命周期，协议标识符及必要的英文术语保持原名。公共入口和容易误用的内部接口，应说明参数、返回值、空值、取消、所有权和副作用。

例如，“保存成功后才发布新快照，避免磁盘失败而页面已显示成功”比“保存数据”更有价值。多阶段安装可用阶段注释说明顺序，但不要逐行翻译赋值语句。新代码不复制过时注释、大段废弃代码、含糊缩写或情绪化命名。

XML 参数文档使用 `<param name="...">`，不能沿用部分旧文件中的 `ID` 或 `Name` 属性。注释必须与实现同步；尤其要准确说明返回新实例还是修改原对象。

## 4. 对象职责、依赖与生命周期

### 4.1 管理器、服务和执行组件

- **Manager**：管理某一类共享状态，提供查询和变更入口，维护数据约束及持久化。
- **Service**：组织一次业务用例，协调管理器与组件，明确完成条件。例如 `VersionInstallerService` 在下载完成后登记版本，再报告最终完成。
- **Provider / Strategy**：封装可替换的供应商、下载来源或加载器差异，接口只包含调用方真正需要的能力。
- **Builder / Parser**：组装命令或解析协议数据，不同时承担窗口交互、全局登记和进程生命周期。
- **会话对象**：持有某一次运行的进度、取消和进程状态；不能与应用级单例混用。

这些角色是职责指引，不要求机械地为每个功能创建五种类型。现有 `LaunchService` 虽以 Service 命名，实际是单次启动会话，应按其真实生命周期使用。

### 4.2 组合与初始化

当前初始化链为：

1. `Init.Initialize` 创建、初始化 `DBManager`，确定路径，创建共享 `Download`，并将这两个实例注册到 `IServiceCollection`。
2. `UnitedCore.Initialize` 初始化版本索引、账户、实例、认证器和其他核心对象，并组装服务。
3. `Init.Initialize` 将完成初始化的 `UnitedCore` 注册到同一个 `IServiceCollection`。
4. 前端 `MainWindow` 补充 ViewModel 和工厂注册，随后构建服务提供器。

因此，当前并不是所有 Manager 都单独注册到容器；不少调用方注入 `UnitedCore` 后使用其属性。新增依赖应接入这个组合位置，不自行 `BuildServiceProvider()`，也不为同一个 JSON 文件重新创建另一个管理器实例。

服务内部优先使用构造函数显式接收所需依赖，并保存到 `private readonly` 字段。只由 Core 组装的服务，可以沿用 `public sealed` 类型配合 `internal` 构造函数的模式。内部执行器使用 `internal`，只有跨程序集调用所需的入口和模型才公开。

`Init` 的注释已经说明其职责向 `UnitedCore` 迁移，后端仍存在 `UnitedCore.Core`、`Init.ConfigManager`、`Init.Download` 等静态访问。维护旧流程时可以保留这些连接，但新增服务优先显式传入依赖；不要把新状态继续堆入 `Init`，也不要把整个静态依赖迁移夹带进一个小功能。

需要 I/O 的对象使用 `CreateAsync` 或显式 `InitializeAsync`，完成后再暴露给调用方。构造函数尽量只赋值、校验和建立必要订阅，不启动无人等待的后台初始化。

### 4.3 共享对象与会话对象

| 对象 | 生命周期 | 约束 |
| --- | --- | --- |
| 数据管理器、`TaskManager`、`JavaManager`、入口服务 | 跟随核心实例 | 不保存某次操作独有的进度或取消状态 |
| `Download` 与共享 HTTP 客户端 | 由初始化入口统一创建和清理 | 借用者不随意释放或修改影响其他调用的全局设置 |
| `LaunchService`、`GameLauncher` | 每次游戏启动独立创建 | 不复用已经启动的会话；持有者负责释放 |
| `DownloadMinecraft` 等执行对象 | 每次安装独立创建 | 当前计数、下载计划及令牌不能跨任务串用 |

`GameLaunchService.CreateLaunchService()` 已明确每次返回新会话，`LaunchService` 也限制只能启动一次。新增类似功能时沿用“共享入口创建独立会话”的方式。事件订阅、进程、临时参数文件、流和取消源的释放责任应明确；`Dispose` 与“停止业务”是不同动作，不应让调用方猜测释放是否会终止游戏。

## 5. 模型、返回值与兼容契约

### 5.1 区分三种数据

- **持久化模型**：例如 `AppConfig`、`GameDataRoot`、`AccountData`、`VersionListData`，字段关系属于磁盘格式契约。
- **外部协议模型**：放在对应组件附近，用 `[JsonPropertyName]` 对接 Mojang、Modrinth、认证服务等字段，避免协议拼写扩散到业务接口。
- **操作输入及过程数据**：例如 `DownloadInfo` 和内部 `DownloadPlan`，保存某一次操作所需的参数和计划。

后端模型不继承 UI 的 `BaseViewModel`。新增模型尽量以属性表达数据，以 `init` / `required` 表达构造要求；简单不可变过程数据可使用 `record` / `readonly record struct`，不因语法偏好改变已有引用语义。`VersionBasicInfo` 源码明确要求保留为类，不能直接改成结构体。

### 5.2 空值和查询

查询未找到可以返回 `T?`，集合查询优先返回空集合。依赖项缺失导致操作无法继续时，应明确抛出异常，不能让非可空返回值悄悄返回 `null`。

不要用 `null!` 代替初始化设计或输入校验。对外说明 `null` 是“未找到”“用户取消”还是“协议未提供”；例如现有微软交互登录用 `UserModel?` 的 `null` 表示取消，调用方需要保留这一兼容语义，不把它当作成功登录。

查询接口尽量返回快照或只读视图。只读集合并不自动使集合内的对象不可变；`VersionListManager.GetVersions()` 同时复制列表和条目，可作为防止调用方绕过管理器修改状态的参考。现有 `Data` 属性仍暴露可变模型，不能据此声称所有 Manager 都已实现状态隔离。

### 5.3 版本与实例不能混用

- `VersionBasicInfo` 描述可下载的版本信息；`UserVersion` 描述已安装版本。
- `GameData` 描述游戏实例，拥有独立 `InstanceId`，并通过 `VersionId` 关联版本。
- `GameDataRoot` 管理实例、默认实例映射和标签；`VersionListManager` 管理当前游戏根目录的版本索引。

新增功能应选取正确的标识符和管理器，不把版本 ID 当作实例 ID，不把同一版本的多个实例当成重复版本，也不将已安装版本重新写回全局设置。

## 6. 异步、取消与并发

### 6.1 异步边界

可等待的操作返回 `Task` 或 `Task<T>`，新增后台业务方法不使用 `async void`。仅转发另一个异步操作时可以直接返回其 `Task`；同步完成的无操作分支可以返回 `Task.CompletedTask`。需要在完成后提交状态、处理异常或释放资源时使用 `await`。

文件、网络和进程等待优先使用对应异步 API，不通过 `.Result`、`.Wait()` 或 `GetAwaiter().GetResult()` 将异步链改回同步。前端启动入口存在同步等待，不作为新增后端方法的范例。`Task.Run` 仅用于确有必要移出当前线程的同步耗时工作，不给所有异步 I/O 再包一层。

必须观察启动的任务。只有在事件桥接等确实无法返回任务的地方才考虑 `_ = SomeAsync()`，并在该方法内部处理故障和生命周期；保存配置、登记版本和完成安装不能使用无人等待的调用。

### 6.2 取消契约

新增可取消入口优先采用末尾参数 `CancellationToken cancellationToken = default`，并传递到网络、文件复制、锁等待、重试延迟等实际操作。适配现有 `CancellationToken?` 接口时，在边界统一转换为 `CancellationToken.None`。

取消通常通过 `OperationCanceledException` 传播，在任务边界映射为取消状态。不要将其包装成“下载失败”，也不要对用户取消进行重试。历史下载组件有收到取消后直接返回的分支，因此调用这些组件的上层必须在登记或宣告成功前再次检查令牌，不能仅以“await 没抛异常”判断成功。

提交边界也应明确：在保存前接受取消；一旦开始一个不能中断的提交，就完成该次提交并保持返回结果与已提交状态一致。当前 `VersionListManager` 在 `CommitAsync` 前检查令牌，`SaveDataAsync` 本身没有取消参数；这不是整个持久化流程都可随时取消的保证。

`Task.WaitAsync(token)` 只让等待方停止等待，不能据此假定被等待的底层操作已停止。创建了子任务的流程，在失败或取消时仍应安排取消及收尾，避免返回后继续写文件或修改共享数据。

### 6.3 并发与锁

- 并发下载和校验必须有明确上限，沿用已有配置及 `Parallel.ForEachAsync` / `SemaphoreSlim`，不要对任意规模输入无限制创建并发工作。
- `WaitAsync` 成功之后进入 `try/finally`，在 `finally` 中释放信号量；等待被取消时不能多释放一次。
- `lock` 仅保护短小的内存读写，不在锁内等待异步 I/O 或执行外部回调。
- `Interlocked` 适合计数或一次性状态；多个字段组成的状态迁移仍需要一致的同步策略。
- 并发容器只能保障自身操作，不能自动保障“读取—合并—保存”或其内部普通集合的业务原子性。

`VersionListManager` 用操作锁串行化读改写，用状态锁保护快照；`JavaManager` 用按 Java 版本划分的锁防止同版本重复安装。参考这些实现时，仍需单独考虑不同版本或不同任务对其他共享配置的访问。

## 7. 进度、事件与任务状态

短期过程信息用 `IProgress<T>`，可被多个调用方观察的状态变化用事件。沿用项目的 `event Action?`、`Action<T>` 风格即可，不为统一形式强行替换全部事件类型。

现有进度有不同单位：`DownProgress` 搭配文件数量、资源下载的字节数量，以及启动任务使用的 0–100 进度。新增接口必须说明阶段、计数单位、未知总量和完成条件。简单的局部进度可继续用具名元组；跨模块共用、需要持续扩充的进度适合独立模型，不继续拉长元组。

业务上的完成必须发生在必要副作用成功之后。版本安装应在文件处理及版本索引登记成功之后报告 `DownProgress.Done`；下载完成数应在对应文件成功完成后递增。不能用“已排队数量”冒充“已完成数量”。

任务状态约定为从 `Running` 进入 `Finished`、`Failed` 或 `Canceled`，终态不应被迟到的进度、进程退出事件或重复异常覆盖。当前 `TaskInstance` 的公开方法没有统一的原子终态保护，调用方仍需防护；`LaunchService` 的状态判断可供参考，但不能推断 `TaskManager` 已保证所有场景都线程安全。

事件默认不保证在 UI 线程执行。`Progress<T>` 的回调调度与创建时的上下文有关，不能笼统承诺“后端回调总在后台线程”。前端按需要切换线程，并在页面、Pane 或会话结束时解除订阅。

发布数据变化时先完成提交，再释放业务锁，最后通知订阅方。对已经成功提交的数据，不应因一个通知订阅者抛错而伪装成保存失败；`BasicDataManager<T>.NotifyDataChanged` 已逐个调用并记录订阅异常。不要将所有普通方法异常都按事件通知的方式吞掉。

## 8. 异常与诊断

使用 `ArgumentException`、`ArgumentNullException`、`InvalidOperationException` 等表达编程契约错误；需要向用户解释的业务失败使用 `OlanException`，包含简短标题、具体原因和可定位的操作上下文。

| `OlanExceptionAction` | 用途 | 现有前端处理 |
| --- | --- | --- |
| `Warning` | 可提示且不要求整个应用停止的情况 | 通知 |
| `Error` | 当前业务操作失败，需要处理 | 错误对话框 |
| `FatalError` | 核心初始化或关键状态无法安全继续 | 对话框后退出 |

转换异常时使用带原异常的构造函数，例如：

```csharp
catch (IOException ex)
{
    throw new OlanException(
        "保存失败",
        $"无法保存配置文件 {configPath}：{ex.Message}",
        OlanExceptionAction.Error,
        ex);
}
```

当前原异常保存在 `OriginalException`，构造函数没有将其传入 `Exception` 基类，不能假定从 `InnerException` 能取得原始原因。原样传播时用 `throw;` 保留堆栈。

只在能够恢复、转换业务语义、标记任务或清理资源的位置捕获异常。批量扫描中跳过无法识别的模组可以有明确的降级策略，但不能将关键保存、认证和安装异常统一转成 `null`、空集合或成功。临时文件清理失败不能覆盖原业务错误；必要时按当前项目的 `Trace` / `Debug` 方式记录。

诊断记录包含阶段、版本、实例和文件路径等必要上下文，不记录访问令牌、密码、认证头或带敏感参数的完整启动命令。已有 `LastLaunchArgs.bat` 写入行为需要单独审查，不作为新增日志代码的模板。`TryAgainFunction` 当前是 `Action`，不能直接塞入产生 `async void` 的异步重试流程。

## 9. JSON 持久化、迁移与 AOT

### 9.1 存储归属

项目长期结构化数据以 JSON 保存，管理器继承 `BasicDataManager<T>`，一个管理器管理对应的数据文件。虽然名为 `DBManager`，当前实现并不是数据库访问层。

| 管理器 | 数据文件 | 负责的数据 |
| --- | --- | --- |
| `DBManager` | `Init.BasePath/config.json` | 全局设置、默认配置、Java 记录和服务器列表等 |
| `AccountManager` | `Init.BasePath/playerdata/account.json` | 用户模型和默认用户 |
| `GameDataManager` | `Init.GameRootPath/instance/instance.json` | 实例、标签及默认实例映射 |
| `VersionListManager` | `Init.GameRootPath/versions/version_list.json` | 当前游戏根目录的已安装版本索引 |

管理器初始化成功后再读取 `Data`。新数据类型通过 `CreateJsonTypeInfo(JsonSerializerOptions)` 返回源生成的 `JsonTypeInfo<T>`，按需实现 `ValidateData`、`PostInitialize`。关键索引可覆写 `RequireValidDocument` 拒绝空文件和 `null`，配合 `[JsonRequired]` 和 `ValidateData` 检查缺失字段及业务约束，不能一律将损坏数据替换为空配置。

### 9.2 保存的语义

`BasicDataManager<T>.SaveDataAsync` 当前先校验，再串行写入同目录唯一临时文件，刷新并关闭流后替换目标文件，最后清理临时文件。新增持久化能力应复用这条路径，不自行直接截断正式配置再写入。

需要失败时内存和磁盘保持一致的变更，应采用 `VersionListManager` 的候选数据方式：

1. 在操作锁保护下，从当前状态产生候选数据。
2. 校验并保存候选数据。
3. 保存成功后发布内存状态。
4. 释放操作锁，随后发送数据变化事件。

普通 `Data.X = value; await Save();` 是现有部分管理器的用法，但基类不会自动回滚此前的内存修改。不要将文件写入锁误认为整个业务变更的事务，也不要承诺临时文件替换已覆盖跨进程写入、多个文件的事务或所有断电情形。

### 9.3 序列化契约与迁移

使用 `System.Text.Json` 源生成上下文和带类型信息的序列化重载。协议字段使用 `[JsonPropertyName]`，运行时计算属性使用 `[JsonIgnore]`；`IJsonOnDeserialized` 可用于恢复字典键与模型 ID 的关系。新增字段或根类型时检查相应上下文，不能只验证普通 JIT 下的反射序列化。

当前 `AppConfig.LegacyVersionList` 通过 `[JsonPropertyName("VersionList")]` 读取旧字段，并在迁移后清空、不再写出。新功能不得继续将它当作版本索引来源。

迁移应保持原文件备份，验证新文件确实保存且可读后再移除旧字段，并能在中断后重试。已有独立索引时不应再次把全局旧列表覆盖进去。可参考 [VersionListMigration.cs](../../OneLauncher.Core/Global/ModelDataMangers/VersionListMigration.cs)。更改 JSON 字段名、枚举值、ID 格式或目录布局时，必须同时设计兼容读取和迁移路径。

新增运行时代码避免依赖无法确认可裁剪性的反射发现、动态生成和隐式序列化元数据。测试程序为了验证内部实现而使用反射，不代表生产代码应复制该做法。

## 10. 文件、网络、进程和平台边界

### 10.1 路径与文件

使用 `Path.Combine`、`GetFullPath`、`GetRelativePath` 等表达路径关系。版本 ID 等单级目录标识应先校验，再用于路径拼接；涉及游戏目录的操作需与对应管理器的根目录一致，可参考 `VersionListManager.EnsureGameRoot`。

外部清单、压缩包条目和导入目录都属于输入，应检查最终目标是否位于允许的根目录内，并考虑实际允许的链接及覆盖行为。不能仅凭字符串拼接或简单前缀匹配判定安全。此条是新增导入、解压逻辑的要求，不表示当前所有导入器已经具备完整路径校验。

文件下载应先写临时文件，必要的长度或散列校验成功后再发布正式目标，失败和取消时清理临时产物。`DownloadFileAndSha1` 可作为这一顺序的参考；`DownloadFileBig` 当前直接写目标文件，不能泛化为所有下载方法都已满足相同的提交语义。并发写同一目标时，还需明确互斥或独立临时文件策略。

### 10.2 网络与资源所有权

优先复用已有下载客户端；认证等需要独立配置的组件可持有专用客户端。每次请求的响应、流和请求对象及时释放，共享客户端的释放由其所有者负责。

当前 `Download.Dispose()` 会释放构造时传入或内部创建的 `HttpClient`，复用时须了解这一实际行为；新接口必须说明传入资源是否转移所有权。普通请求借用共享客户端时，不随意修改其默认认证头、超时等共享设置。

重试必须有上限，仅针对可恢复故障，延迟接受取消。多源竞速既要处理获胜请求，也要观察并清理其他请求及响应；取消其他源不能提前中断获胜源的正文读取。分段下载需要验证服务器真实支持 Range、分段范围和长度，不能将 HTTP 200 当成预期的分段响应。

### 10.3 进程与平台

启动命令由 `LaunchCommandBuilder` 和加载器策略生成，进程执行由 `GameLauncher` 承担，任务及事件由 `LaunchService` 协调。新增加载器差异应接入对应策略，而不是在 UI 中拼接 JVM 参数。临时参数文件需要存活到子进程实际完成读取，不能仅以构建命令结束作为释放时机。

明确进程输出、退出、停止和释放的顺序；取消等待不等于进程已被终止。命令参数中的路径、空格和特殊字符应通过已有参数构建机制处理，避免未经处理地拼接为 shell 命令。

当前项目目标框架为 `net10.0`，启用 nullable；发布目标由仓库构建属性和 RID 决定。平台专用引用和 API 使用 `ONELAUNCHER_TARGET_WINDOWS`、`ONELAUNCHER_TARGET_LINUX`、`ONELAUNCHER_TARGET_MACOS`；确实需要判断运行环境的文件系统或平台行为可以使用 `OperatingSystem` / `RuntimeInformation`。不能根据开发机是 Windows 就给所有目标启用 Windows 组件。

新增平台分支时同时检查对应包引用、非该平台分支的行为及发布配置。当前 Release 构建要求显式 RID，支持范围以 [Directory.Build.targets](../../Directory.Build.targets) 为准，不能将本机 Debug 构建通过等同于跨平台或 Native AOT 验证通过。

## 11. 扩展现有功能的落点

| 要扩展的能力 | 主要落点 | 需要同步考虑 |
| --- | --- | --- |
| 新增长期保存的数据 | 数据根模型、`BasicDataManager<T>` 子类、JSON 上下文 | 初始化、归属文件、校验、迁移、通知 |
| 新增业务流程 | `Services` 中的入口，必要的内部执行组件 | 依赖组装、取消、完成条件、错误和生命周期 |
| 新增 Java 提供商 | `IJavaProvider`、适用时复用 `BaseJavaProvider`、`JavaManager` 的选择逻辑 | 平台与架构、版本限制、安装路径、失败清理 |
| 新增下载来源 | `IDownloadSourceUrlProvider` 及 `DownloadSourceStrategy` 选择逻辑 | 目标文件一致、官方源保留、竞速及校验 |
| 新增模组加载器 | 安装 Provider 与启动 `IModArgStrategy` | 依赖获取、安装处理器、元数据解析、参数构建、枚举及持久化兼容 |
| 新增前端可观察的变化 | 对应 Manager 或会话的事件 / 进度接口 | 事件时机、线程、订阅解除，不以轮询补接口 |

新增类先确定职责和生命周期，再决定是否需要接口、继承或 `partial`。参考一个实现时，应参考它的局部职责，不把其中的静态访问、无界异常捕获或拼写问题一并复制。

下面是参考 `VersionInstallerService` 的新增接口写法示意。现有公开方法仍叫 `InstallNewVersion`，无需仅为本文示例改名；省略了命名空间、依赖字段和构造函数。

```csharp
public async Task InstallNewVersionAsync(
    DownloadInfo info,
    IProgress<(DownProgress Title, int AllFiles, int DownedFiles, string DowingFileName)> progress,
    CancellationToken cancellationToken = default)
{
    ArgumentNullException.ThrowIfNull(info);
    ArgumentNullException.ThrowIfNull(progress);
    _versionListManager.EnsureGameRoot(info.GameRootPath);
    cancellationToken.ThrowIfCancellationRequested();

    var downloader = new DownloadMinecraft(info, progress, cancellationToken);
    await downloader.MinecraftBasic();

    // 旧下载组件存在取消后直接返回的路径，登记前需要再次确认。
    cancellationToken.ThrowIfCancellationRequested();
    await _versionListManager.RegisterInstalledVersionAsync(
        info.VersionInstallInfo,
        cancellationToken);

    progress.Report((DownProgress.Done, downloader.alls, downloader.alls, "下载并登记完毕！"));
}
```

这个例子的重点是入口校验、依赖协调、取消检查和提交后的完成通知；现有进度元组中的 `DowingFileName` 等拼写按接口保留，并不是新类型的命名示范。

## 12. 维护与验证要求

评审新增或修改的后端逻辑时，重点检查：

- 职责是否放在当前实际编译的模块，公开 API 是否只暴露调用方需要的能力。
- 依赖是否来自已有组合入口，共享状态与单次会话是否分开。
- 输入、空值、路径和版本 / 实例标识是否有明确契约。
- 异步任务是否被观察，取消是否贯穿实际操作，并且不会被误报成功或失败。
- 并发读改写、锁释放、任务终态和事件时机是否一致。
- 保存失败是否保留旧数据，迁移是否保留备份、可重试，JSON 上下文是否同步。
- 流、HTTP 响应、临时文件、进程和事件订阅是否有明确的所有者和释放时机。
- 平台条件、序列化和新增依赖是否符合现有构建及 AOT 方向。

按行为风险选择验证，不为纯排版或本文档变更添加测试。持久化与迁移改动重点验证旧格式、损坏输入、失败重试及并发变更；任务与启动改动重点验证取消、重复回调和会话隔离。测试应使用隔离目录、可控网络替身或无网络输入，避免操作真实用户配置。

现有验证入口为 [tests/OneLauncher.RegressionTests/README.md](../../tests/OneLauncher.RegressionTests/README.md)。它是独立可执行检查程序，不是主解决方案内的常规测试项目，需单独构建并运行；覆盖包括版本迁移、并发登记、保存失败和启动依赖图。真实下载、登录、联机和 Native AOT 发布不在其覆盖范围内。

以下命令在仓库根目录执行，适用于实际代码变更时按需验证；`--no-restore` 的前提是相应依赖已经还原：
