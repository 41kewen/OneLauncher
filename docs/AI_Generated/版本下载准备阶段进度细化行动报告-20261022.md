## 1. 建议与目标

将目前笼统的准备提示细分为“版本元数据 → 原版库 → 资源索引 → 资源清单 → 主文件/日志配置 → 所选加载器及可选 API → 本地文件检查 → 下载计划就绪”。每个耗时操作开始前上报、成功后上报结果；长循环按真实处理数量上报。

沿用现有下载文件进度，另外增加准备阶段的结构化回调。准备计数与下载计数分别显示，不把“已收集 3000 条资源信息”解释为“已下载 3000 个文件”。不通过定时增加百分比模拟进展。

预期收益是用户能知道当前在等待什么、哪些部分已经收集完成、接下来是什么。细化上报本身不保证缩短网络请求时间。本报告基于静态代码检查，尚未测量各阶段实际耗时，不能断言某个请求就是本次卡顿的唯一原因。

## 2. 现状与代码依据

### 2.1 第一段空白：下载上下文创建

`OneLauncher/Views/Panes/PaneViewModels/DownloadPaneViewModel.cs` 的 `ToDownload()` 先执行 `await DownloadInfo.Create(...)`，之后才创建 `progressReporter`。

`OneLauncher.Core/DefaultComponent/Downloader/DownloadMinecraftProviders/DownloadInfoCreater.cs` 的 `Create()` 会在没有本地 `version.json` 时下载它，然后读文件并构造 `VersionInfomations`。这部分没有进度回调，下载和读文件也没有接收该任务的取消令牌。

因此，即使细化后面的 Planner，点击下载之后仍可能先出现一段没有反馈的等待。需要把准备回调的创建提前到 `Create()` 之前。

### 2.2 第二段空白：生成下载计划

`DownloadMinecraft.cs` 的 `MinecraftBasic()` 只在 `CreateDownloadPlan()` 前后报告一次 `DownProgress.Meta`，中间细节完全不可见。

`DownloadMinecraftPlanner.cs` 的 `CreateDownloadPlan()` 实际顺序为：

1. 调用 `GetLibraries()` 收集原版库。
2. 获取资源索引描述；不存在时下载索引。
3. 读取索引，调用 `VersionAssetIndex.ParseAssetsIndex()` 生成资源清单。
4. 获取主文件和可选日志配置。
5. 创建所选加载器 Provider，并逐个等待 `GetDependencies()`。
6. 汇总清单，对全部文件、库、资源、加载器文件分别调用 `CheckFilesExists()`。

其中 `CheckFilesExists()` 检查存在性和已知长度，不执行 SHA1 校验。文案应是“检查本地文件”，避免让用户误以为已完成最终完整性校验。

### 2.3 加载器准备包含网络和安装包处理

| 分支 | 当前实际工作 | 可上报的信息 |
| --- | --- | --- |
| Fabric | 请求 Meta，选定加载器，保存元数据，解析库；按选项请求 Modrinth Fabric API | 当前加载器、元数据已获取、库数量、正在查询 API、API 信息获取结果 |
| Quilt | 请求 Meta，保存元数据，解析库；按选项请求 Modrinth QSL | 与 Fabric 相同，使用 Quilt/QSL 名称 |
| Forge | 选定版本/安装器 URL，下载安装包，解析配置，提取版本 JSON 和补丁，汇总依赖库 | 正在选定版本、下载安装包、解析安装配置、提取必要文件、依赖数量 |
| NeoForge | 与 Forge 共用安装包准备器 | 使用 NeoForge 名称，分别上报相同准备步骤 |

Forge/NeoForge 的 `ForgeSeriesInstallTasker.StartReadyAsync()` 会实际下载整个安装包；这不是纯粹的“收集链接”。建议明确显示“正在下载 Forge 安装包，完成后解析依赖”。

`GetModrinth.Init()` 还会逐个请求依赖项目，因此“查询 Fabric API/QSL”内部也可能耗时较长。第一期至少显示该子阶段；逐依赖请求细化见后续增强。

### 2.4 前端和任务中心的信息损失

下载面板将所有 `Meta` 映射为“准备元数据...”，并用文件数计算百分比，准备时通常是 `0/0` 和 `0%`。

虽然 `FileName` 可以显示元组的第四项，但任务中心只收到 `task.SetProgress(Dp, progressPercentage)`，没有收到第四项，因而看不到准备细节。

当前 50ms 节流也会跳过短阶段的标题更新。新方案需要保证阶段开始、阶段结束、取消、失败与完成不被节流过滤。

仓库中没有检索到“收集下载信息”这一完整字面量；本报告对应当前实现中的“准备元数据”和“正在生成下载计划”链路。

- 只显示用户选择的加载器与 API 分支；未选择的步骤不列为未完成。

## 4. 建议更改的代码契约

以下为设计示意，未写入源码，具体声明在实施时与项目风格对齐。

### 4.1 新增准备进度模型

新文件：`OneLauncher.Core/DefaultComponent/Downloader/DownloadMinecraftProviders/DownloadPreparationProgress.cs`。

```csharp
public enum DownloadPreparationStage
{
    VersionMetadata, Libraries, AssetIndex, Assets, MainAndLogging,
    LoaderMetadata, LoaderInstaller, LoaderConfiguration,
    LoaderDependencies, OptionalModMetadata, LocalFileScan, Ready
}

public enum PreparationState { Started, Advanced, Completed }
public enum PreparationUnit { None, Entries, Files, Bytes }

public sealed record DownloadPreparationProgress(
    DownloadPreparationStage Stage,
    PreparationState State,
    string? Component, // Fabric、Forge、原版资源等，不使用类型名猜测
    string Detail,
    long? Completed = null,
    long? Total = null,
    PreparationUnit Unit = PreparationUnit.None);
```

约定：未知总数为 `null`；`Completed` 的含义由 `Unit` 和阶段决定。`Completed` 状态表示该步骤确实成功完成，不等于整个版本安装完成。Core 上报业务事实，前端负责标题、摘要和比例展示。

### 4.2 为现有入口追加可选回调

```csharp
// 在现有参数末尾追加，保留原参数名称、顺序与旧调用形式：
DownloadInfo.Create(...,
    IProgress<DownloadPreparationProgress>? preparationProgress = null,
    CancellationToken cancellationToken = default);

VersionInstallerService.InstallNewVersion(...,
    IProgress<DownloadPreparationProgress>? preparationProgress = null);

DownloadMinecraft(...,
    IProgress<DownloadPreparationProgress>? preparationProgress = null);

IModLoaderConcreteProviders.GetDependencies(
    IProgress<DownloadPreparationProgress>? preparationProgress = null,
    CancellationToken cancellationToken = default);

ForgeSeriesInstallTasker.StartReadyAsync(...,
    IProgress<DownloadPreparationProgress>? preparationProgress = null,
    CancellationToken cancellationToken = default);

Download.CheckFilesExists(...,
    IProgress<(int Checked, int Total)>? checkProgress = null);
```

`InstallNewVersion()` 将回调传给 `DownloadMinecraft`；Planner 再传给所选 Provider。`DownloadInfo.Create()` 由前端直接传入同一回调。

现有 `DownProgress` 及四元组保持原有含义，不添加必须修改所有旧 `switch` 的准备阶段枚举值。没有新回调的调用者继续得到原有粗略 `Meta` 报告。下载面板接入新回调后，忽略会覆盖细分提示的粗略 `Meta` 更新。

### 4.3 在真实工作边界插入上报

```csharp
// 示例：在索引下载前报告等待，完成后再报告成功。
preparationProgress?.Report(new(
    DownloadPreparationStage.AssetIndex, PreparationState.Started,
    "原版资源", File.Exists(index.path)
        ? "正在读取本地资源索引" : "正在下载资源索引"));

// 原有下载/读文件操作；网络下载、异步读文件传入任务令牌。
// 获取或读取失败时直接抛出，不上报 Completed。

preparationProgress?.Report(new(
    DownloadPreparationStage.AssetIndex, PreparationState.Completed,
    "原版资源", "资源索引已获取"));
```

Planner 在 `GetLibraries()`、资源清单解析、主文件/日志获取、每个 Provider 和每组本地检查前后添加同类报告。收集完成时从列表读取真实数量，而不是估算。

`CheckFilesExists()` 每处理一项递增检查数，开始报告 0/总数、结束报告最终值。中间按固定条目批次或约 100ms 上报，避免几千次 UI 调度。已有筛选、长度检查与异常行为保持原有业务语义。

Forge 准备器在 HTTP 请求前、安装包接收完成后、JSON 解析前后、文件提取前后上报。第一期安装包下载使用不确定进度；若要显示字节数，必须进一步采用响应头读取和流复制计数，不能把“请求已发出”报告为“安装包已下载”。

### 4.4 前端创建回调与处理时序

`ToDownload()` 在进入后台工作前、UI 线程上创建两种 `Progress<T>`，之后将其传入 `Create()` 和安装服务。避免当前在后台创建 `Progress<T>`、再额外 `Dispatcher.Post` 的多重调度。

准备回调更新：阶段标题、当前详情、累计收集摘要、检查计数和 `IsPreparationIndeterminate`。摘要只根据成功的完成报告更新，按类别替换数量，不能因为重复报告而累计两次。

阶段变化和阶段完成立即更新；只有同阶段密集计数报告被合并，且必须保留最后一条待显示快照。UI 渲染节流与后台任务完成逻辑分开。

一旦任务取消、失败或完成，忽略迟到报告；进入正式下载后，忽略迟到的准备报告，防止界面倒退到准备状态。准备 `Ready` 不调用 `task.SetDone()`，最终完成继续由现有安装完成协议决定。

## 7. 实施顺序与验收

1. 先实现 Core 模型、可选参数与真实工作边界上报，验证旧调用兼容。
2. 再接入下载面板和任务中心文本，完善阶段切换、摘要与节流。
3. 完成离线回归、构建和人工下载验收，回填报告。

应验证的行为：

- 没有本地版本 JSON 时，在等待 HTTP 返回前已经显示“获取版本元数据”；已有 JSON 显示读取本地文件。
- 原版、Fabric、Fabric + API、Quilt、Quilt + QSL、Forge、NeoForge 各路径只显示实际执行步骤。
- 已有资源索引与首次下载索引都能正确显示；不需要日志配置时显示无需该项。
- 本地检查的 x/y 来自实际扫描；几千条密集报告不会造成 UI 队列堆积，最后计数一定显示。
- 网络请求暂未返回时显示不确定进度；成功后切换下一步骤；失败时保持失败结果。
- 取消后和正式下载开始后，迟到准备回调不能覆盖当前状态。
- 下载面板与任务中心显示同一个实际步骤，面板另保留已完成类别摘要。
- 收集数量、扫描数量和下载数量不混用；准备完成不被解释为安装完成。
- PCL2 与整合包旧调用能编译，既有回归检查继续通过。

离线检查优先使用可控进度源和临时文件；需要模拟 HTTP 等待/异常时使用替代消息处理器或隔离夹具，不依赖官方服务器。不为了测试新增全局初始化或读取真实用户配置。

构建建议沿用仓库现有方式：`dotnet build OneLauncher/OneLauncher.csproj --no-restore` 与回归项目构建、运行。真实在线请求时序和加载器安装包路径仍需人工验收；离线展示检查不能代替真实下载验收。

本次仅完成阅读和静态分析，未执行构建、下载或测试，以上均为待实施后的验证要求。

## 8. 实施边界

发现 Planner 当前重复扫描文件集合、多 Provider 情况下汇总逻辑可能重复添加加载器条目，以及已有下载文件计数语义问题。这些会影响性能或最终百分比，但不应在进度细化过程中顺便改写下载/校验业务。实施时保持原有清单语义，展示数量使用清楚的“条目数”措辞；相关修复单独评估。
