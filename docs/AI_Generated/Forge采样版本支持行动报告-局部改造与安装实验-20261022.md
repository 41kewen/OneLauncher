## 1. 结论与边界

**保留现有 Download → Mod Provider → ForgeSeriesInstallTasker，以及 Launcher → IModArgStrategy 的调用链，足以实施六个 installer 样本的主要安装和启动适配。无需采用旧报告的全项目清单、revision、通用 ArtifactStore 或 LaunchSession 重构。**

但“指定范围内完成局部改造”和“七个采样版本通过完整产品验收”不能直接画等号。实验发现两个必须正面处理的边界：

1. **Minecraft 1.1 是 JarMod，不存在本次所探测坐标的 installer.jar。** 官方提供 client ZIP；只将它叠加到原版，实际类加载会因缺少 `BaseMod` 失败。还涉及历史前置组件、旧启动参数和资源目录。当前通用启动构建器没有提供策略替换整套游戏参数的接口，前端也明确禁用了 1.1 的 Forge 选项。它必须继续保留为原目标中的独立工作项，不能用“暂不支持”冒充七个版本已经完成。
2. **`MainClassToModEnum(string)` 的输入不足以准确判断所有 Forge/NeoForge。** 原版 1.1 与旧 Forge 共用 LaunchWrapper；现代 Forge 与实际拆包的两个 NeoForge 样本共用 BootstrapLauncher。将其中任一主类无条件映射为 Forge 或 NeoForge，都会产生可复现的误判。

推荐执行顺序为：先完成六个 installer 样本的局部安装和启动能力，再解决 1.1 的前置输入与最小启动接口缺口；最后依据验收结果去掉产品中的“预览”。本报告不会把前六个的成功外推为七个全部支持，也不会把外部官方安装成功说成 OneLauncher 已经安装或启动成功。

### 3.2 旧协议：universal 文件名与落盘名字不同

1.7.10、1.8.9 的包没有根目录 `version.json`，没有 `data/client.lzma`，版本数据就在 `install_profile.json.versionInfo`。安装器从 `install.filePath` 指定条目取得 universal JAR，按 `install.path` 的 Maven 坐标写入库目录。

例如 1.7.10 包内是：

```text
forge-1.7.10-10.13.4.1614-1.7.10-universal.jar
```

官方安装后却是：

```text
libraries/net/minecraftforge/forge/1.7.10-10.13.4.1614-1.7.10/
  forge-1.7.10-10.13.4.1614-1.7.10.jar
```

两个安装后 JAR 与各自内嵌条目的 SHA-1 完全一致：

| MC | 安装后 Forge JAR SHA-1 |
| --- | --- |
| 1.7.10 | `25fd97f72beca728112256938e03e8105b1b78cc` |
| 1.8.9 | `beda619c465af293e63952dd573c137c17c0a4cd` |

旧 `libraries` 只有 `name`、可选 `url`、`checksums`、`clientreq/serverreq` 等字段，不能强行读取 `downloads.artifact`。缺省 Maven 下载根、历史 checksum 候选和普通 JAR 的可用性必须处理。官方日志中的 `Trying unpacked library` 表明这些样本走到了普通 JAR 下载，不足以声称本轮验证了 Pack200 解包。

另一个易误判点：旧官方安装动作会跳过部分 `clientreq` 未标记库，让 launcher 根据版本 JSON 补齐。因此不能直接复制安装动作的过滤结果作为最终启动 classpath。OneLauncher 必须依据版本 JSON 的运行时依赖和原版继承信息准备启动所需文件。

### 3.3 1.12.2：零处理器仍然是有效安装

`14.23.5.2860` 使用 `spec=0`，`json=/version.json`，`processors=[]`；Forge JAR 位于 installer 的 `maven/` 中，对应 `downloads.artifact.url` 为空。校验 SHA-1 为 `029250575d3aa2cf80b56dffb66238a1eeaea2ac`。

这说明：

- 是否有 lzma 与“能否安装 Forge”无直接等价关系。
- 空 URL 不一定是坏包，也不能送给普通 HTTP 下载器；应先检查包内 Maven 条目及生成者。
- 准备完运行库、提取 Forge 库、核验版本数据，即可完成这一协议的安装步骤；不需要伪造一个 processor。

本轮校验器还记录了一项值得保留的“未找到”：profile 声明的 `mcp_config:1.12.2-20200226.224830@zip` 没有被官方客户端安装写出。它不是该版本的运行库，且该样本没有客户端 processor 使用它。实际运行库的已声明摘要均通过。因此这是**无条件并集下载/终检会过度要求无用文件**的证据，不是此次官方安装失败。

### 3.4 现代 profile：原版 JAR → 转换 → patched JAR

1.16.5 的四步客户端流程为：

```text
MCP_DATA → jarsplitter → SpecialSource → binarypatcher
```

1.19.2 和 1.20.1 的六步为：

```text
MCP_DATA → DOWNLOAD_MOJMAPS → MERGE_MAPPING
         → jarsplitter → ForgeAutoRenamingTool → binarypatcher
```

执行 side 为 `client` 或未指定 side 的步骤，保持原数组顺序；不运行服务器专用 `BUNDLER_EXTRACT`、服务端文件提取等步骤。

`MC_SRG` 是映射转换后的输出，不能用“把原版复制为 MC_SRG”代替转换。这种复制在当前代码中随后可能被真正的转换步骤覆盖，所以本报告不声称它必然让所有现代样本失败；但它制造了错误的先验产物，必须移除。

三个现代样本的 `MC_SLIM`、`MC_EXTRA`、`PATCHED` 九项 SHA-1 均匹配 profile，且七份原版 JAR 均未改变。patched 客户端摘要如下：

| MC | `PATCHED` SHA-1 |
| --- | --- |
| 1.16.5 | `427f13ce6f486c182c9693e94e907e2eb049773f` |
| 1.19.2 | `35a6870ac548ae8b7aac55fa8b59f829a6758ee2` |
| 1.20.1 | `b268fd6fb2c4829a72e8d0d6c75b7fefbec8479c` |

重复安装的差异也很重要：1.16.5 的 splitter 和 binarypatcher 有明确 outputs，可验证后跳过；1.20.1 的最后两个步骤没有 outputs，官方重复安装仍执行它们。不能把 `outputs` 的空集合当作“全部已满足”，也不能认为 data 中有 `PATCHED_SHA` 就表示官方 processor 已替调用方检查了这个输出。本轮对后两样本的 PATCHED 摘要是另行独立核验的。

### 3.5 1.1：实测失败原因与后续任务

官方 1.1 页面提供 client/server/src ZIP。本轮探测 `1.1-1.3.4.29-installer.jar` 的既有 HTTP 结果为 404，其保存文件是错误响应，不是有效 JAR；有效研究输入是 client ZIP。

本轮将该 ZIP 叠加到已验证的原版副本，排除 `META-INF`，写成新的 `forge-only-overlay.jar`。记录显示覆盖 77 个已有条目，写入 142 个补丁文件，原版 SHA-1 保持不变。随后执行：

```text
Class.forName("mod_MinecraftForge", false, classLoader)
```

结果为退出码 1、`NoClassDefFoundError: BaseMod`。归档中也确实缺少 `BaseMod.class`、`ModLoader.class`、`ModLoaderMp.class` 等历史前置类。官方源码 ZIP 的开发安装 README 指示使用含 ModLoader 与 ModLoaderMP 的输入；这是历史前置条件的来源证据，**该开发安装脚本不是玩家客户端 installer，本轮没有执行它**。

因此 1.1 的待完成工作必须包括：找到并固定兼容前置组件的可信输入、验证覆盖顺序、生成独立 patched JAR、验证旧启动参数及 assets 布局，最后启动游戏验收。本轮没有取得并验证这些历史前置构件，不能声明“补丁文件已经合并，所以 1.1 支持完成”。

在允许目录内可先实现 JarMod 包识别和明确错误诊断，保留该分支的后续安装适配点；不要猜测某个旧 universal URL、把 ZIP 当 installer 执行，或替换共享原版 JAR。

### 4.1 不应重复制造的“修复项”

- `Tools.MavenToPath` 当前已经支持无 classifier 的 `@zip` 和有 classifier 的 `@txt`；需要局部输入校验，不应再声称它完全不会解析这些形式，也不扩大 Tools 的修改范围。
- ForgeStrategy 将绝对 `versionPath` 传给 `Init` 的表达不够清楚，但 .NET `Path.Combine` 遇绝对路径会重置前缀；不能直接判为“必然拼出双重 versions”。可在白名单内改成直接接受版本 JSON 路径以澄清契约。
- `GetLibrariesForLaunch` 参数注释写成 libraries 路径，但实际调用传的是游戏根，函数再加一次 libraries；当前调用不等于必然重复 `libraries/libraries`。真正需要去掉的是对全局 `Init.GameRootPath` 的依赖，改用 strategy 的 `_basePath`。
- 六个运行库集合在本轮并未出现 group/artifact 重复，`ToDictionary` 冲突是模型缺陷和需要测试的边界，不应谎称七个样本全部已复现该异常。
- 当前 `VersionInstallerService` 已在下载完成并登记版本后报告 Done，不能照搬旧报告中的所有完成事件描述。
- 当前 Download 的缓存检查已有长度判断，普通下载提交也已有后续修改；本方案只针对已确认的 Forge 局部缺口，不再要求替换整个下载器。

## 5. 局部实现方案：继续使用现有 Provider

### 5.1 只增加一个准备结果，不增加全局安装架构

将当前返回 `(versionLibs, installerLibs, lzmaPath)` 的内部契约改成一个局部 `ForgePreparedInstall`，由同一个 Provider 持有到 `RunInstaller`。建议字段：

```text
LoaderKind / MinecraftVersion / ArtifactVersion / InstallerSha256
Protocol = LegacyProfile | Profile0 | Profile1 | JarMod
OriginalVersionJson / ParsedVersion / InstallProfile
RemoteDependencies / EmbeddedEntries / GeneratedRequirements
SelectedClientProcessors / InstallerBytesOrVerifiedCachePath
```

它只是 Forge 安装内部的准备结果，不进入 GameData，不要求替换 DownloadPlan，不成为全项目“完整启动清单”。未知 schema/spec、缺少必要引用、包内 MC 与请求不一致时明确失败。检测优先检查 profile 结构；JarMod 需要受控的历史包身份，不因“没有 profile”就把任意 ZIP 当 1.1 Forge。

### 5.2 GetDependencies 与 RunInstaller 的职责

`GetDependencies()` 保持现有接口：

1. 确定并冻结完整构件身份；推荐/最新只在选择阶段解析一次。
2. 下载并验证 installer，读取 profile/版本清单，准备局部状态。
3. 返回真正需要下载的远程依赖；保留其完整集合用于后续核验，不能只记住此次缺失文件。
4. 此时不提交 `version.forge.json`，不执行 Java，不把 lzma 路径当成功标志。

`RunInstaller(progress, token)`：

1. 建立本次操作的独立工作目录；校验原版 JAR、远程依赖和固定输入。
2. 提取实际引用的内嵌 Maven 库及 data 资源，按预期路径和摘要核对。
3. 对零处理器分支直接进入产物验收；其他分支执行客户端处理器。
4. 校验 Forge 相关最终运行库、模块路径、生成产物及版本配置引用。
5. 最后提交 `version.forge.json`；可相邻保存小型 `version.forge.install-state.json`，记录精确构件、包摘要和应有产物，供后续诊断/同构建修复使用。
6. `finally` 收尾本次子进程和工作目录；异常沿 Task 返回，进度事件只报告事实，不在异步事件处理器里抛异常代替安装失败。

现有入口会先下载原版 client，并在运行 mod installer 前等待 Java 安装，这个顺序可以复用。`GetDependencies()` 本身没有 CancellationToken 参数，因此白名单内只能提供网络超时等局部约束，不能声称元数据阶段已经具备完整取消传播。

### 5.3 库的解析与校验

区分四类，并让“来源”与“是否用于运行”分别表示：

| 类别 | 处理 |
| --- | --- |
| Remote | 以 JSON 显式 URL/摘要为先；legacy 由 name 与仓库根推导；交给现有 Download 或局部校验后重取 |
| Embedded | 从 installer 条目取出并验证；旧 universal 使用 `install.filePath → install.path`，新包检查 `maven/<artifact.path>` |
| Generated | 由已选客户端 processor 生成；安装前不发空 URL 下载请求 |
| Unused declaration | 没被运行库、所选 processor 或输入引用使用的 profile 声明，不当作客户端成功的必需文件 |

对于安装依赖，可先保守准备有客户端处理器时的 profile 库集合，再逐步缩至引用闭包；**它们不能全部加入游戏 classpath**。运行 classpath 取版本 JSON 的运行库；某些 Forge 主产物及组件由 FML 按路径发现，需额外列入产物验收，不因未直接出现在 classpath 就遗漏。

旧 checksums 允许候选集合；没有长度/摘要要记录验证强度，不虚构值。传统库是否用于启动，以运行版本清单和规则为准，不机械复制旧官方 installer 的 clientreq 过滤逻辑。对仅有 Pack200 的更老构件另行明确能力边界；这两个旧样本的结果不构成 Pack200 支持证据。

Forge 自己的终检应包含已存在缓存，检查存在性、可用摘要和 JAR 结构。当前 DownloadPlanner 会先筛选文件，公共 SHA-1 检查会跳过缺失文件；因此不得把它当作 Forge 完整性的唯一依据。局部发现坏缓存时，重取到临时文件、验证后提交，不要求改造整个共享下载系统。

### 5.4 处理器执行

- side 过滤、顺序、主类、classpath、args 均由包内协议决定，不按文件名猜算法。
- 实现 Maven、`{KEY}`、带单引号 literal、归档资源引用的局部解析；未知引用、循环引用或越界归档路径失败。hash 字符串不按文件路径创建目录。
- 使用 `ArgumentList` 逐项传参；工作目录、处理器输入输出都明确落在本次受控目录。其作用是避免误写项目和路径错误，不声称能隔离 Java 的全部系统权限。
- Main-Class 读取支持 manifest 的续行；捕获并等待 stdout/stderr 完成，真实非零退出码失败；stderr 有文字本身不是失败判据。
- outputs 非空且全部摘要通过才允许跳过；空 outputs 必须执行。运行后检查声明 outputs，并在最后校验已识别版本形态的必要产物，包括后两样本的 PATCHED。
- 取消时终止进程树并等待退出，再清理工作目录。当前 Tasker 只调用 Kill、未完成子进程树及双流收尾，可在 Mod 内修正。
- `DOWNLOAD_MOJMAPS` 初期可以按官方步骤执行，本轮已验证可成功。需要统一代理和下载策略时，再在 Mod 内针对确切 task/side/version/output 接管，使用该 MC 官方 metadata 的 client_mappings URL 和摘要；未验证下载成功不得跳过 Java 步骤。

### 5.5 提交与并发边界

只对 Forge 局部配置实行“先准备、后校验、最后替换”，工作目录在失败时可清理，已安装配置保留至新产物通过。固定构件的缓存可以共享；不同 MC 的工作目录分离。

但是现有调用方同时运行原版库/资源下载，且缺少贯穿整个任务的失败收尾和事务回调。Provider 内的锁也无法约束公共 Download 在调用 Provider 之前的写入。因此此方案**不承诺跨所有下载任务、登记和启动进程的原子事务**；初期限制同一游戏根/MC/loader 槽位不要并发升级或边运行边重装。不能为追求这种承诺，再偷偷引入旧报告的全局事务架构。

相邻 install-state 与版本 JSON 也不是天然的双文件原子事务；版本 JSON 保持启动必需事实，辅助状态只能用于匹配校验和恢复诊断，不能在提交中断后指向另一构建并被盲信。

## 6. Launcher 侧：在 Strategy 中补足协议差异

### 6.1 主类与游戏参数

| 样本 | 主类 | Strategy 必须保留的加载器参数 |
| --- | --- | --- |
| 1.7.10 | `net.minecraft.launchwrapper.Launch` | `--tweakClass cpw.mods.fml.common.launcher.FMLTweaker` |
| 1.8.9、1.12.2 | `net.minecraft.launchwrapper.Launch` | `--tweakClass net.minecraftforge.fml.common.launcher.FMLTweaker` |
| 1.16.5 | `cpw.mods.modlauncher.Launcher` | 包内 `--launchTarget fmlclient` 及精确 `--fml.*` |
| 1.19.2、1.20.1 | `cpw.mods.bootstraplauncher.BootstrapLauncher` | 包内 `--launchTarget forgeclient` 及精确 `--fml.*` |

现有 `BuildGameArgs` 已生成用户名、token、gameDir 等公共参数。legacy Strategy 应将 `minecraftArguments` 按 token 解析，输出加载器增量，例如 `--tweakClass`，不能将整串官方参数再次追加，造成重复账户/路径选项。对于 `--versionType Forge` 等非装载关键的公共选项差异应显式记录；在当前接口下不应依赖“后一个同名参数一定覆盖前一个”。

现代样本的 `arguments.game` 可以作为加载器增量保留；不存在的 `arguments.jvm/game` 返回空集合而非空引用异常。JNI、assets、账户等公共配置继续由现有 Launcher 负责。

1.1 的 Mojang 清单则使用位置参数 `${auth_player_name} ${auth_session}`、`--assetsDir ${game_assets}`。当前 Builder 用 `--username ... --session ...` 和通用 assets 根，Strategy 只提供“追加参数”，也拿不到本次完整账户/gamePath 上下文，故无法诚实地把 1.1 问题归结为“补一个 tweakClass”。

### 6.2 classpath 与 module-path

- ForgeSeriesUsing 解析 legacy 库路径，使用传入 `_basePath`，不要依赖全局根目录。
- 与当前基础 classpath 字典保持覆盖键兼容：默认 JAR 采用 `group:artifact`，classifier 使用 `group:artifact:classifier`；额外扩展名只在确有需要时形成区别键。若一律改成 `group:artifact:@jar` 而不改 Builder，反而无法覆盖基础库，这是需要避免的新错误。
- 保持顺序、使用索引赋值处理重复项；运行库与安装工具库分离，后者不同版本的 ASM/Guava 不能混入运行环境。
- 保留现代 Forge 的 `-p`、`--add-modules`、`--add-opens`、`--add-exports`、ignore/merge 参数，替换 `${library_directory}`、`${classpath_separator}`、`${version_name}`。
- Strategy 最终参数要兼容现有 `LaunchCommand` 的字符串 join 合同：对有空格的单个路径/属性值做一次正确编码；不要在此仅把逻辑 token 改成裸字符串就认为项目已经使用 ArgumentList。
- 当前 legacy `BuildJvmArgs` 分支不会调用 Strategy 的额外 JVM 参数。上述三个 LaunchWrapper 样本可主要用 tweak 参数接入，但凡额外 JVM 设置成为必要条件，就需要确认该白名单外接口缺口。

### 6.3 Java 与启动完成判据

本次固定样本采用 Java 8 / Java 17 与 Mojang metadata 的版本要求一致，可复用现有 JavaManager。不要为了新 Forge 而把所有旧样本提升到 Java 17。

安装器退出、处理器结束、启动主类可解析、游戏进程创建、游戏主菜单正常显示是不同层级。发布验收要求至少进入主菜单、确认对应 Forge 构建、装载兼容小型测试 Mod、进入并退出测试世界，再以已有入口重复启动。真正的游戏过程尚未在本轮验证。

## 7. MainClassToModEnum 与 NeoForge 的正确边界

本轮额外拆包：

| 身份 | 完整 artifact | MC | 主类 / 关键信息 |
| --- | --- | --- | --- |
| 早期 NeoForge | `net.neoforged:forge:1.20.1-47.1.106` | 1.20.1 | BootstrapLauncher；`forgeclient`；同时依赖 net.minecraftforge 与 net.neoforged.fancymodloader |
| NeoForge | `net.neoforged:neoforge:20.2.93` | 1.20.2 | BootstrapLauncher；仍为 `forgeclient`；含 `--fml.neoForgeVersion` |

两个包的 profile `path` 还均为空，说明不能要求每个现代包必须通过该字段标识身份。身份应来自已选下载构件及包内有效证据；完整 URL/coordinate、版本参数和 loader 库组合相互核对。

这证明以下规则都不可靠：

- BootstrapLauncher = NeoForge。
- LaunchWrapper = Forge。
- launchTarget 为 forgeclient = Forge。
- 存在任意 `net.minecraftforge:*` 库 = Forge。
- NeoForge 一律由 `<MC去掉1.>` 前缀在 `net.neoforged:neoforge` 中查找；1.20.1 使用另一 artifact。

**受当前仅修改判断方法的限制，建议保留单参数方法，但对共享入口显式报告“仅凭主类无法判断”，不要再返回一个错误的具体加载器，也不要悄悄降为原版。** 唯一已知的 loader 主类可以继续精确匹配；陌生主类的历史默认行为与共享入口的已知歧义分开处理。

当前该方法的生产调用者是 `Helper/ImportPCL2Version/ImportMain.cs:48`，正常 Download/Launcher 已有用户选定的 ModEnum，无需重新猜测身份。因此明确拒绝歧义主要影响导入边界，不阻断用户已选择 Forge 的正常安装与启动。

若需要让这些 PCL 导入也准确工作，就必须另行允许调用方提供 libraries、tweakClass、fml 参数或精确来源信息；只有给方法增加可选参数、却不修改调用方，并不能解决问题。本轮不将 PCL 导入全功能列为 Forge 六样本的局部实施前置项。

NeoForge 后续可复用修正后的 profile 解析与执行器，但身份和目录分别保存，不能在两者之间共享版本 JSON 或由 `isForge` 猜补丁行为。此次只做了两个 Neo 包的结构探测，未完成 Neo 安装、产物或游戏启动验收。

## 8. 如何参考 ProjBobcat，而不搬入另一套架构

参考快照固定为 `57532e29f73e38e64d809893a81518eb9f10d1a3`，与既有源码 ZIP 对应；本轮直接读取了该快照的三个安装器实现。

| ProjBobcat 实现 | 可借鉴 | 不宜直接照搬 |
| --- | --- | --- |
| `ForgeInstallerFactory` | 历史构件后缀处理、检查归档内容 | 以少数版本规则代替 Maven 精确身份；仅用 universal 文件名猜协议 |
| `LegacyForgeInstaller` | 读取 `versionInfo`；将 universal 提取到 Maven 目标 | 其“安装成功”不代表本项目全部运行库、assets 和启动已通过 |
| `HighVersionForgeInstaller` | 内嵌 Maven 提取、data/processor 解析、预下载 Mojmap、side 过滤 | 字符串拼命令、仅以 stderr 内容判断错误、把解析 outputs 当作已校验 |

在所读快照中，HighVersion 实现将 outputs 存入处理器模型，但该执行循环没有据此完成输出验收；它等待进程后检查 stderr 是否有文本，却没有对应的退出码判断。故新 Tasker 应使用“真实退出码 + 输出产物校验”，不能以参考库存在这段代码就认为行为已经足够。

参考中的 legacy 安装器也没有覆盖本次 1.1 JarMod 及其前置条件。它有助于明确六个 installer 样本的落地方式，不能替代 1.1 的单独研究。

| 官方重复安装 | 已做 1.16.5、1.20.1 | 正确跳过有 outputs 的有效步骤，运行空 outputs 步骤 |
| 1.1 叠加与前置类探测 | 已做，失败原因明确 | 取得兼容前置后安装及启动均通过 |
| OneLauncher Download→Launcher | 未做 | 七个目标分别记录结果；不能用六个通过覆盖第七个 |
| 游戏主菜单、Mod、世界、重启 | 未做 | 无缺库/模块错误，加载器版本正确，正常退出 |
| 坏缓存、坏 SHA-1、缺失生成输出 | 待实现测试 | 不因存在/退出码 0 就报成功；修复使用固定构件 |
| 取消、处理器非零退出、失败后重试 | 待实现测试 | 及时失败、进程收尾、旧有效配置可继续使用 |
| 空格/中文/长路径、跨平台 | 未做 | Windows 先实测；Linux/macOS 需各自验证，不由本机结论外推 |
| NeoForge 两包 | 仅拆包 | 后续独立安装与启动验收 |

单元/fixture 测试重点放在协议分型、旧库路径、重复 classifier、空 outputs、占位符失败、库覆盖键、legacy 增量参数和共享主类歧义。生产路径集成测试要走真实入口，不能只调用新 Parser 然后宣布 Launcher 已支持。测试工程若也严格禁止修改，可先放研究目录独立运行；正式纳入 tests 作为单独测试交付安排，不扩大业务源码边界。
